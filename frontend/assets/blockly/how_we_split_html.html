How We Split index.html

A Step-by-Step Guide to Breaking a 5.7 MB Single File

into Clean, Separated, Cacheable Files

Blockly Project — rndmfg

1. What Was the Problem?

Your project had a single file called index.html that contained everything — HTML layout, CSS styles, JavaScript logic, 3D models, and icons — all packed into one file.

The Problem: The file was 5.7 MB and 19,517 lines long. A normal HTML file should only be a few hundred lines.

What was inside the single file?

ContentSizeShould it be in HTML?
HTML structure (divs, buttons)~82 KBYes
CSS styles (inline <style> blocks)~179 KBNo — use a .css file
JavaScript logic (inline <script> blocks)~505 KBNo — use .js files
3D model: soil_sensor.glb (base64)1,072 KBNo — use a .glb file
3D model: bike.glb (base64)2,478 KBNo — use a .glb file
58 SVG icons (base64)~108 KBNo — use .svg files

Why does this cause trouble?

  • Slow to load: The browser must download all 5.7 MB before showing anything.
  • No caching: Every page visit re-downloads 5.7 MB, even if nothing changed.
  • Hard to edit: VSCode slows down opening a 19,000-line file.
  • Memory pressure: On a Raspberry Pi or tablet, it can crash or lag badly.
  • Bad Git history: A tiny code change shows a huge diff.

2. The Solution — What We Did

We split the single file into separate files. The browser still loads the same page — it just fetches the pieces separately now, and can cache each piece independently.

Before

1 file: index.html (5.7 MB) All CSS, JS, models, and icons crammed inside one HTML file. Re-downloaded fully every visit.

After

7+ files (total same size) Each file is cached separately. Second visit loads almost instantly.

3. Step-by-Step Process

1

Take a Backup First

Before touching anything, we made a copy of the original file. This is the most important step — if anything goes wrong, you can always restore.

copy index.html  index.html.bak
Why? The original file is your safety net. Never modify a big file without a backup.
2

Extract CSS — Move <style> Blocks to a .css File

Inside your HTML there were 9 separate <style>...</style> blocks. We copied all the content between those tags into a new file css/main.css, then deleted those blocks from the HTML.

Before (inside index.html):

<style>
  body { margin: 0; }
  .navbar { background: #1e1b4b; }
  /* ... thousands of lines ... */
</style>

<style>
  /* ... more styles ... */
</style>

After (index.html has just one line):

<link rel="stylesheet" href="css/main.css" />

New file: css/main.css contains all the style content:

body { margin: 0; }
.navbar { background: #1e1b4b; }
/* ... all styles combined ... */
Result: HTML lost ~179 KB. The browser now downloads main.css once and caches it. Next visit: CSS loads from cache instantly — no download needed.
3

Extract JavaScript — Move <script> Blocks to .js Files

There were 5 large <script>...</script> blocks in the HTML. We saved each one as a numbered JS file, then replaced each block with a single <script src="..."> reference.

Important — Two scripts stayed inline: The very first script (12 lines) sets up screen height for mobile. It MUST run before anything else loads, so it stays inside the HTML. We only moved the large blocks (>40 lines) to external files.

Before (inside index.html):

<script>
  window.toolboxConfig = {
    kind: 'categoryToolbox',
    contents: [
      /* ... 343 lines of block config ... */
    ]
  };
</script>

<script>
  let workspace = null;
  /* ... 9,445 lines of main logic ... */
</script>

After (index.html):

<script src="js/block_01.js"></script>
<script src="js/block_02.js"></script>
<script src="js/block_03.js"></script>
<script src="js/block_04.js"></script>
<script src="js/block_05.js"></script>
Result: HTML lost another ~505 KB of script content. Each JS file is cached separately — only changed files need to re-download.
4

Extract 3D Models — Remove Base64 GLB from JavaScript

Two 3D model files (GLB format used by Three.js) were stored as enormous base64 text strings inside the JavaScript. Base64 is a way to encode binary files as text — but it makes the text ~33% larger than the original binary.

What is base64?

Base64 explained simply: Binary files (like images, 3D models) contain bytes that can't be typed as plain text. Base64 converts them to letters and numbers so they can be put inside a text file (like HTML or JS). The downside: the result is 33% larger, and the browser can't cache it separately.

Before (inside js/block_02.js):

const _BIKE_GLB_B64 = "Z2xURgIAAAAQuiYANEABAEpTT0..."; // ← 3.4 MB of text!

// To load it, the code did this:
const binStr = atob(_BIKE_GLB_B64);           // decode base64 to binary string
const u8 = new Uint8Array(binStr.length);      // convert to byte array
for (let i = 0; i < binStr.length; i++)
    u8[i] = binStr.charCodeAt(i);
const blobUrl = URL.createObjectURL(          // create a temporary URL
    new Blob([u8.buffer], {type: 'model/gltf-binary'})
);
new THREE.GLTFLoader().load(blobUrl, ...);

After (js/block_02.js):

// The GLB file now lives at assets/models/bike.glb
// Load it directly — no base64 decode needed:
const blobUrl = 'assets/models/bike.glb';
new THREE.GLTFLoader().load(blobUrl, ...);

The actual GLB files were decoded and saved:

assets/models/soil_sensor.glb   ← 1,072 KB binary file
assets/models/bike.glb          ← 2,478 KB binary file
Result: Removed 4,847 KB (4.7 MB!) of base64 text from the JS file. The 3D models load faster because the browser fetches the binary directly — no decode step.
5

Extract SVG Icons — Remove Base64 Images from CSS and JS

58 icon images (SVG format) were embedded as base64 strings inside the CSS and JavaScript. For example, the CSS had background image rules like this:

Before (inside css/main.css):

.icon-digital {
  background-image: url("data:image/svg+xml;base64,PHN2ZyB3aWR0aD...");
  /* ↑ a very long base64 string for a tiny SVG icon */
}

After (css/main.css):

.icon-digital {
  background-image: url(../assets/img/img_001.svg);
  /* ↑ just a path to the real file */
}

The actual SVG files were decoded and saved:

assets/img/img_001.svg
assets/img/img_002.svg
... (58 files total)
Result: CSS shrank from 5,518 KB to 179 KB — because the images are now real files. SVG files are also cached by the browser.
6

How the Python Script Did This Automatically

Doing all of the above by hand on a 19,517-line file would take days. We wrote a Python script (split_html.py) that did everything automatically.

The script worked in 4 passes:

# Pass 1: Read the entire file into memory
with open("index.html", "r", encoding="utf-8") as f:
    lines = f.readlines()

# Pass 2: Walk through every line using a "state machine"
#   - When we see <style>, start collecting CSS lines
#   - When we see </style>, stop — save collected lines to css/main.css
#   - When we see <script> (no src=), start collecting JS lines
#   - When we see </script>, stop — save to js/block_N.js
#   - Replace each removed block with a <link> or <script src> reference

# Pass 3: Scan css/main.css for base64 SVG patterns
#   url("data:image/svg+xml;base64,...") → decode → save as .svg file
#   Replace the long base64 with: url(../assets/img/img_001.svg)

# Pass 4: Scan js/block_02.js for GLB base64 constants
#   const _BIKE_GLB_B64 = "huge string..." → decode → save as .glb file
#   Replace the 5-line atob() decode with: const blobUrl = 'assets/models/bike.glb'

# Write the new slim index.html
with open("index.html", "w", encoding="utf-8") as f:
    f.write(new_html)
What is a "state machine"? A state machine is a program that knows what "state" it is in. In our case, the states were: "reading normal HTML", "inside a <style> block", or "inside a <script> block". This prevented the common bug where <style> text inside a JavaScript comment would be mistakenly treated as real CSS.

5. How the Browser Loads the Page Now

When a user opens your page, the browser does this:

1

Downloads index.html (82 KB) — very fast. Starts showing the page structure.

2

Sees <link href="css/main.css"> — downloads the CSS (179 KB). Applies styles.

3

Sees the 5 <script src="js/block_NN.js"> tags — downloads each JS file. Runs them in order.

4

When the 3D model viewer opens, downloads assets/models/bike.glb or soil_sensor.glb on demand — only when needed.

On second visit: The browser checks its cache first. CSS, JS files, GLB models, and SVG icons are all served from local cache — near-instant load. Only index.html (82 KB) is re-checked for updates.

6. Key Concepts Explained Simply

What is Base64?

Binary files (images, 3D models) are made of bytes — raw data that can include any value 0-255. HTML and CSS are text files that can only safely contain printable characters. Base64 converts binary data to only 64 safe characters (A-Z, a-z, 0-9, +, /). This lets you paste a binary file directly inside a text file. The cost: the result is 33% larger than the original.

What is Browser Caching?

When you visit a website, the browser saves (caches) files like CSS, JS, and images on your device. The next time you visit, the browser uses the saved copies instead of downloading again. This only works for separate files — inline content inside HTML is never cached separately.

What is a State Machine?

A state machine is a program that can be in one of several "states" and changes state when it sees certain triggers. Our parser had 3 states: Normal, InStyle, InScript. When the parser was in "InScript" state, it ignored any <style> text it saw — preventing it from being accidentally treated as CSS.

What is GLB / GLTF?

GLTF (GL Transmission Format) is a standard file format for 3D models, created by Khronos Group. GLB is the binary version of GLTF — a single file containing the 3D geometry, materials, and animations. It is used by Three.js (the 3D library in your project) to display 3D objects in a browser.
